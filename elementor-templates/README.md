# Elementor templates

## `location-page.json`

The Austin, TX location page (`design/location-pages/austin-tx.html`), expressed as the
payload Elementor's own `elementor/build-composition` MCP tool accepts. Generated by
`scripts/build_elementor_location_composition.py` — regenerate from that script rather than
hand-editing the JSON; it validates configuration-id uniqueness, XML well-formedness, and
that every referenced class label is actually defined before it writes the file.

### Why this format, not a raw document JSON

Elementor's atomic settings/styles use a type-tagged `{"$$type": ..., "value": ...}` wire
format. This project could not verify that format against a live Elementor instance — no
site access, no reachable MCP proxy from this sandbox, `wp-env`/Docker unavailable here —
and styles fail **soft** on a mismatch (silently unstyled, not an error). Shipping a
hand-guessed raw document JSON risked the exact failure this whole exercise exists to avoid:
looks fine, discover it's broken later.

`elementor/build-composition` sidesteps that: it takes plain XML + plain `element_config` +
plain CSS text, and Elementor's own server does the type-wrapping and CSS-to-atomic-props
conversion. That input shape is read from the MCP module's own committed guidance
(`modules/mcp/static-resources/abilities/build-composition.md` in `elementor/elementor`,
`main` @ 2026-08-13), not reconstructed from memory, so it's the one representation of this
page this project can stand behind.

**Trade-off, stated plainly:** `elementor/build-composition` is not in a released Elementor
version yet — see `docs/elementor-authoring.md` §1 and §5. This file is ready for the moment
it is (or for a self-hosted MCP client, if one exists in your setup already).

### How to use it today (no MCP yet)

1. Confirm the four prerequisites in `docs/elementor-authoring.md` §9 (Elementor 4.0.x, the
   `e_opt_in_v4` experiment enabled, a staging site, no colliding global class/variable
   labels).
2. Open `design/location-pages/austin-tx.html` side by side with the Elementor editor on a
   new `location` CPT entry (or a scratch page while the CPT is being set up). Every string
   in this JSON's `composition.element_config` is the exact, final copy — this is
   transcription against a finished design, not new copywriting or layout decisions.
3. Build top-down through `composition.xml_structure`: each `<e-tag configuration-id="...">`
   is one Elementor element. Its `element_config[configuration-id]` entry is the widget's
   settings panel content; its `style[configuration-id]` entry (where present) is CSS to
   paste into that element's Style tab (Elementor's own CSS-class field, or the "Custom CSS"
   equivalent for one-off local styles — longhand only, matching what's here); its
   `classes[configuration-id]` entry lists which global classes from `global_classes` to
   attach.
4. Create `global_variables` first (Site Settings → Variables in a V4 kit), `global_classes`
   second (each entry's `style` is plain CSS, same longhand rule), **then** the page content
   — same order Elementor's own guidance specifies, because classes reference variables and
   elements reference classes.

### How to use it once `elementor/build-composition` is reachable

Send the three parts in order, into the `single-location` template's content:

1. `elementor/manage-global-variable` once per entry in `global_variables`.
2. `elementor/manage-classes` once per entry in `global_classes`.
3. `elementor/build-composition` with the `composition` block as-is
   (`parent_id: "document"`, `mode: "replace_children"`).

Then `elementor/create-preview-link` and eyeball it before publishing — this JSON has not
been round-tripped through a real Elementor instance, so that first look is the actual
verification step, not a formality.

### What's deliberately not in here

- **The FAQ is always-visible Q&A, not a click-to-expand accordion.** `<details>` (used in
  the HTML prototype) has no atomic Elementor equivalent in the released widget set.
  Per the "atomic first, mature V3/Pro widget where V4 has no equivalent" policy
  (`docs/elementor-authoring.md` §1a), the click-to-expand version is Elementor Pro's native
  Accordion widget — same five questions/answers, dropped in by hand since the composition
  tool's XML only understands `e-*` atomic tags and named site-part/component references.
- **The nav and footer are not in this composition.** They're shared sitewide chrome and
  belong in Elementor's Theme Builder header/footer, not duplicated per location page.
- **The 8 nearby-area pills link to sibling location pages that don't exist yet**
  (`/locations/round-rock-tx/` etc.). This is the interlinking *pattern* from
  `docs/elementor-authoring.md` §7, not a claim those pages are live — swap for a
  dynamic-tag repeater over the location taxonomy once the CPT exists.
- **Two FAQ answers and the hero/CTA copy are Austin-specific text**, not dynamic tags bound
  to post fields — this is a concrete, finished page for one city, not yet the templated
  version. Converting the city-specific strings to dynamic tags against the `location` CPT
  fields (`docs/elementor-authoring.md` §7) is the mechanical next step once that CPT is
  built on the live site — a decision for that build, not something to fabricate here.
