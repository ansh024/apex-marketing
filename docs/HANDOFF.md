## Decisions already made, do not relitigate

- **Elementor Pro is active**, so the end state is ONE dynamic template over a `location` CPT, not
  N duplicated pages.
- **The design system lives in the Elementor kit, not a custom theme.** Global variables plus
  global classes are the single source of truth; header and footer are Theme Builder parts; other
  pages are Elementor pages on the same classes. A custom theme was considered and rejected: its
  only real advantage is a single home for the design system, which the kit already provides, and
  its cost is putting that system somewhere only a developer can change. Full reasoning in
  `docs/elementor-authoring.md` §1b.
- **The homepage stays a hand-coded plugin PHP template, as a documented exception.** Its canvas
  relief, hero sweep, GSAP scroll work and halftone footer cannot be expressed in the atomic style
  schema. Three costs, accepted knowingly: the homepage and the kit are two systems kept in sync
  **by hand**, the homepage is not client-editable, and the plugin's stylesheet dequeue is
  load-bearing for the exception. If the homepage is ever ported into Elementor, deleting that
  dequeue is step one.
- **Design target for location pages is the "calm, pure-Elementor" version.** The homepage's
  effects do NOT travel. No plugin CSS dependency on location pages.
- **Atomic elements first**, falling back to a mature V3/Pro widget where V4 has no equivalent.
  Never an HTML widget full of markup, which is what made an earlier blog template unusable.
- **Exclusivity policy**: no blanket category exclusivity, decided case-by-case on the audit call.
  Confirmed with the business; both the location page and `template-apex-landing.php` now say this.

## How location pages differ from the homepage, and why it is not a design question

The first version was structurally the homepage with a city word inserted. The design critique's
sharpest question was: *if you deleted every instance of "Austin," what would remain that a Cedar
Park visitor couldn't get from the homepage?* The answer was eight suburb pills.

**That is an information problem and cannot be designed around.** Restyling makes the page look
different while it stays the same page underneath, and near-duplicate content across twenty city
pages is exactly what local SEO punishes. So the page differs by what it *contains*:

- **First 30 days** (dated timeline of what happens after the call). Not on the homepage. Sitewide
  truth, so no invented local detail needed.
- **Three things to ask whoever runs your ads now** (objection handling vs the local operator).
  Ruled columns, deliberately not cards, so it does not repeat the services grid.
- **Coverage grouped by county** (Travis / Williamson / Hays) rather than a flat pill row.
- **The standalone founder section was removed** and folded into the booking section as a byline,
  where "who am I talking to" is useful at the point of decision. It was identical on every page.

**The ceiling, and the single highest-value thing anyone can do for these pages:** the four
strongest differentiators are all blocked on data that does not exist yet. A live account count in
the metro, a named local client who consents, a real market CPL or cost per appointment, or one
local testimonial. Any **one** of those is worth more than every section listed above. None can be
invented. Until one exists, these pages have a hard ceiling on how different they can be, and that
is a content problem for the business, not a design problem to solve in the repo.

## Constraints that cost real time to discover

- **Never register a location page as one of the `apex-landing-page` plugin's PHP page templates.**
  `apex-landing-page.php:205-217` dequeues every stylesheet except a five-handle allowlist, which
  would strip Elementor's own CSS. The CPT route is naturally safe because both guards test
  `is_page()`, which is false for a CPT single. **That dequeue is load-bearing for the homepage
  exception and must never be widened.**
- **Atomic elements are gated behind the `e_opt_in_v4` experiment, default off.** Templates using
  them import as empty elements until it is enabled.
- **Global Elementor variables cannot hold a `clamp()`** (a Size variable is a structured
  `{size, unit}` pair). Only flat tokens ported; the fluid type scale stays literal CSS with
  `@media(--breakpoint)` steps.
- **Longhand CSS only** (`padding-top`, not `padding`) and **Elementor breakpoint names only**
  (`@media(--mobile)`, never raw pixel queries). Both fall back to `custom_css`, which Pro 3.35+
  strips.
- **Styles fail soft, settings fail hard.** A malformed style silently produces an unstyled
  element, which is why the payload avoids hand-written `$$type` JSON.
- **Zero em-dashes anywhere visible.** taste-skill §9.G, zero tolerance. Middots max one per line.
- **The copy rule that matters:** a line either says something only true in that city, or says the
  sitewide sentence unchanged. Half-localisation ("built around Austin's highest-value
  neighborhoods") is what reads as machine-written and is the specific thing the last pass fixed.
- **Do not fabricate local proof.** No invented client names, city-specific stats, or "we know this
  market" claims.
- **The data voice is for facts and labels, never sentences.** Setting a full sentence in tracked
  uppercase is what the detector flags as `all-caps-body`. This regressed once already.
- **Do not repeat a layout family.** Nine sections currently use nine different arrangements
  (asymmetric hero, stat band, card grid, dated timeline, clause stack, ruled columns, county
  columns, ruled Q&A, split form). Adding a section means adding a new arrangement, not reusing
  the card grid.

## What's left

**Needs the business, not a developer. Highest value on the list:**
1. **Get one real local fact.** A live account count in the metro, a named client who consents, a
   real market CPL, or one local testimonial. This is the ceiling on the whole page type and
   outranks every build item below. It goes in the hero survey plate in the data voice.
2. Confirm whether Apex has a physical Texas presence. Nothing in the repo establishes it
   (toll-free number, gmail address, no street address anywhere), so the page currently neither
   claims nor denies one. If there is a real presence, saying so is the strongest single addition
   available.

**Needs a human on the live site (unreachable from a sandbox):**
3. Elementor version is 4.0.x.
4. The `e_opt_in_v4` experiment is enabled. Do it on staging first, it changes the editor sitewide.
5. Whether a staging site exists.
6. Whether the kit already has Theme Builder header/footer parts, and whether global class or
   variable labels would collide (import merges by label).

**Build work:**
7. Register the `location` CPT and its fields. Nothing exists yet. Fields sketched in
   `docs/elementor-authoring.md` §7; services, nearby areas and FAQs are repeaters and need a shape
   decision (taxonomy vs ACF repeater vs fixed fields).
8. Get the Austin page into Elementor, either by transcribing from `location-page.json` or by
   submitting it if `elementor/build-composition` has shipped. Two manual steps either way, both
   listed in the payload's `manual_steps` array: the GoHighLevel booking form as an HTML widget,
   and optionally the FAQ as a Pro Accordion.
9. Build the Theme Builder header and footer once, from the homepage's nav pill and footer.
   Location pages currently carry their own copies for the standalone prototype only.
10. Convert the city-specific strings to dynamic tags once the CPT exists. Which strings are local
    is documented in `design/location-pages/README.md`.
11. The area pills are plain text, not links, because the sibling pages do not exist. They become
    dynamic links when the CPT ships.

## What I'd do next

Item 1, and it is not close. Everything in the build list produces a better-built version of the
same page; one real local number changes what the page *is*. If that is blocked, item 7 (the
`location` CPT) is the highest-value build work, since it is the only real code left and it
unblocks 8 through 11.
